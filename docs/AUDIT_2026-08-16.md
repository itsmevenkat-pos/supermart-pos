# SuperMart POS — Repository Audit & Status Report

**Date:** 2026-08-16 · **Commit context:** `main` @ `948e43d` (PR #2 merged), branch `feature/phase2-enterprise` ahead by 3 docs commits, **PR #3 open/unreviewed**
**Scope:** `lib/` (244 files, 48,926 LOC), `test/` (46 files, 10,822 LOC), `docs/`, `tasks/`, project config
**Method:** static review of the working tree. `flutter analyze` and `flutter test` were **not re-run** — no Flutter SDK is reachable from this sandbox. Analyzer/test figures below are quoted from `tasks/phase2/PROGRESS.md` and labelled as such.

---

## 1. Verdict

This is a genuinely substantial application — 30 feature modules, double-entry GL, bank reconciliation, loyalty, payment gateways, collections and commission, all backed by 567 tests and four architecture documents. The engineering discipline in the Phase 1/Phase 2 work is high: transactional integrity is taken seriously, gaps are recorded rather than hidden, and the `tasks/*/PROGRESS.md` files are among the better project journals I've read.

The risk is no longer *"is it built?"* — it is **the gap between what the codebase claims about itself and what it does**, in three specific places:

1. **Cash controls.** The shift reconciliation that is supposed to catch till fraud has a hole big enough to drive the whole khata-collection flow through.
2. **Test confidence.** 100 of the 567 tests assert nothing about this application. They cluster on billing, tax, stock and payments.
3. **The live reference doc is wrong.** `README.md` points at `FEATURE_STATUS.md` as the source of truth; it is materially contradicted by the code in at least seven places.

None of these is a rewrite. All three are days, not weeks.

## 3. Critical findings

### C1 — Shift cash reconciliation ignores every non-sale cash movement

`counter_close_screen.dart:163`

```dart
final expectedCash = session.openingCash + _cashSalesSoFar;
```

`_cashSalesSoFar` comes from `SaleRepository.getCashTotalBySession()`, which sums **only** `sales.payment_methods['cash']` where `status = 'completed'`. Nothing else in the app contributes to expected cash. Cross-checking the writers:

- `customer_repository.receivePayment()` — **no `session_id` column is written at all.** Khata cash collected during a shift never reaches the reconciliation.
- `sales_return_repository` / `sale_cancellation_repository` — no `session_id`; a cash refund leaves the drawer without reducing expected cash.
- `exchange_repository.dart:48` is the only one of the four that carries `sessionId` through, and it inherits it from the return header rather than posting a cash movement.

**Failure scenario.** A cashier opens with ₹2,000, rings ₹18,000 of cash sales, and collects ₹5,000 of khata dues over the shift. Expected cash reads ₹20,000; the drawer holds ₹25,000. The cashier can remove exactly ₹5,000 and close a perfectly balanced till. Symmetrically, a ₹3,000 cash refund on a return makes an honest cashier read ₹3,000 short and start hunting a phantom error.

This is the single highest-value defect in the repository: the control that exists specifically to detect till shrinkage is blind to the two transaction types most used to create it.

**Fix.** Give cash movement one writer. Add a `cash_movements` table (`session_id`, `direction`, `amount`, `source_type`, `source_id`, `user_id`), write to it from sale, return, cancellation, exchange and customer payment inside each existing transaction, and compute `expectedCash` as `openingCash + SUM(cash_movements)`. That also gives you the cash-book the GL currently lacks.

### C2 — `/credit/receive-payment` is ungated, unapproved and unaudited

`receive_payment_screen.dart` contains no role check, no `requireApprovalWithApprover` call, and no `logAudit` call — grep returns zero matches for all three. The route is absent from `_routeMinRole`, so it is open to every logged-in role including cashier.

The screen reduces a customer's receivable. Combined with C1, a cashier can accept ₹5,000 cash, record it against the customer's khata, remove the cash, and leave no approval record, no audit row and no reconciliation discrepancy. This is textbook lapping, and every control that would normally catch it is either absent or blind here.

Returns, exchanges and cancellations are handled correctly by comparison — `exchange_form_screen.dart:253` and `sale_cancel_form_screen.dart:154` both require manager/admin approval unconditionally, and returns gate on a configurable threshold (`return_form_screen.dart:251`). Receive-payment is the outlier, not the norm.

**Fix.** Route it through `requireApprovalWithApprover` above a configurable threshold (mirroring returns), write a `logAudit` row on every receipt, and stamp `session_id` (which C1's fix needs anyway).

### C3 — Sale cancellations still don't post to the GL

Already recorded in `FEATURE_STATUS.md` §15 and re-flagged in all four Phase 2 task retrospectives — verified still true: `sale_cancellation_repository.dart` has **zero** references to `GLService`, while `sales_return_repository.dart:145` correctly calls `postSalesReturnEntries`.

Consequence, stated precisely (and the Phase 2 notes state it well): `customer_ledger` *does* record cancellations, so aging and the receivable are right, but the GL is not. Revenue reads high for any period containing cancellations, and the GL receivable disagrees with the ledger receivable. Three Phase 2 modules (bank reconciliation, gateways, collections) now depend on that disagreement being understood.

`reverseByReference` already exists and is the right tool. This is the highest-value Phase 1 follow-up and has been flagged as such five separate times without being picked up.

## 4. High findings

### H1 — 100 of 567 tests (17.6%) never touch application code

Twenty test files have no uncommented `import 'package:supermart_pos/…'`. They assert arithmetic on local constants. In full, from `test/integration/complete_sale_test.dart`:

```dart
const subtotal = price * quantity;
expect(subtotal, 500.0);
```

That is a test of Dart's `*` operator, filed under "Complete Sale Integration". Several files still carry the scaffolding comment that was never resolved:

```dart
// TODO: Replace with your actual billing service import.
// import 'package:supermart_pos/core/services/billing_service.dart';
```

| File | Fake tests |
|---|---|
| `test/core/business_logic/pos_business_logic_test.dart` | 8 |
| `test/core/services/billing_service_test.dart` | 8 |
| `test/core/services/stock_service_test.dart` | 8 |
| `test/core/services/payment_service_test.dart` | 7 |
| `test/repositories/product_batch_repository_test.dart` | 7 |
| `test/core/services/tax_service_test.dart` | 6 |
| `test/repositories/sales_return_repository_test.dart` | 6 |
| `test/core/services/barcode_service_test.dart`, `loyalty_service_test.dart`, `test/core/database/product_database_test.dart`, `test/integration/grouped_product_stock_test.dart` | 5 each |
| 9 further files | 1–4 each |

The distribution is the problem. These 20 files are named for **billing, tax/GST, stock, payments, barcode, returns, the sale repository and every "integration" test** — precisely the surfaces where a POS loses money. The genuinely rigorous 467 tests sit on the GL and the four Phase 2 modules.

The concrete blind spot: **`sale_repository.dart` has no real test.** It is the most consequential file in the codebase — invoice numbering, atomic stock deduction, kit component explosion, loyalty accrual, customer ledger writes and GL posting all live there — and its only nominal test file, `test/repositories/sales_repository_test.dart`, is one of the 20.

**Fix.** Delete all 20 files in one commit; the count drops to 467 and stops lying. Then write real `sqflite_common_ffi` tests for `sale_repository` first, following the pattern already established in `test/repositories/gl_repository_test.dart` — that pattern is good, it just was never applied backwards.

| §5 *"Coupon codes… not built"* | `coupon_repository.dart` + `billing_screen.dart:735` validate/apply/record-usage flow |

| §9 *"No `supabase_flutter` dependency in `pubspec.yaml`, no `supabase` string anywhere in `lib/`"* | `pubspec.yaml` declares `supabase_flutter: ^2.5.0`; `supabase_sync_service.dart` exists |

| §11 *"the **only** caller [of `logAudit`] in the entire codebase is `price_override_guard.dart`"* | 6 callers: loyalty service, exchange repo, cancellation repo, return screen, product form, price guard |

Every one of these errs the same way — it *understates* the app. Nobody is going to ship a bug because of it, but a new contributor or an automated run reading `FEATURE_STATUS.md` as instructed will rebuild things that exist. That is exactly the failure mode `tasks/phase2/PROGRESS.md` warns about in its closing paragraph: *"before implementing anything a task file calls new, grep for it."* The same rule now needs applying to `FEATURE_STATUS.md` itself.

Two claims in it **do** still hold and are worth keeping: `gst_service.dart` is still an 11-line stub, and the GST tab still shows one aggregate rather than a compliance report (see M6).

### H3 — Route gating fails open

`app_router.dart` maps 40 of 63 route paths in `_routeMinRole`. Anything absent is reachable by every logged-in role. The comment says so plainly and the design is deliberate, but the default direction is wrong for an application that moves money: **adding a route grants universal access unless the author remembers to restrict it.**

Of the 23 currently ungated routes, most are correct and intentional (billing, holds, quotations, sales history — cashiers need these). Two are not:

- `/credit/receive-payment` — see C2.
- `/customers/form` — a cashier can set or raise `creditLimit` (`customer_form_screen.dart:73`) with no approval and no audit row, then sell on credit against the limit they just wrote.

**Fix.** Invert the default: require an explicit `_routeMinRole` entry, and have an unmapped path fall through to admin-only plus a test that asserts every `GoRoute` path appears in the map. That converts "forgot to gate it" from a silent privilege grant into a failing test.

### H4 — Repositories and services are constructed inside widgets

52 `SomeRepository()` and 22 `SomeService()` direct instantiations inside `lib/features/`, plus 6 direct `DatabaseHelper` uses in UI code. Riverpod is present and used for state (99 files import `flutter_riverpod`), but data access largely bypasses it.

This is why there are **zero widget tests** — nothing can be substituted, so no screen can be rendered against a fake. The `AppScaffold` `ListTile`/`Container` assertion documented in `FEATURE_STATUS.md` §15 is usually cited as the blocker, but it is the second one; even with that fixed, screens would still reach straight into SQLite.

**Fix.** These are already largely uniform constructor shapes (`XRepository({DatabaseHelper? db})`), so wrapping each in a `Provider` and swapping `XRepository()` for `ref.read(xRepositoryProvider)` is mechanical. Do it per feature as you touch them rather than in one sweep.

## 5. Medium findings

**M1 — Money is `double` throughout.** 133 money-typed fields across the models; the GL compensates with `balanceTolerance = 0.01` and `FinancialStatementService.tolerance = 0.01`. Defensible for a single-shop POS and clearly reasoned about in comments, but it means "balanced" is an approximation in a double-entry system, and it will not survive multi-store consolidation. If you ever revisit it, integer paise is the cheap version of the fix; `Decimal` is the thorough one.

**M2 — Five files over 1,000 lines.** `billing_screen.dart` (1,847), `purchase_form_screen.dart` (1,444), `reports_screen.dart` (1,238), `advanced_report_service.dart` (1,140), `settings_screen.dart` (1,059); 23 files over 500. `billing_screen.dart` holds the keyboard-wedge handler, MRP selection, coupon entry, loyalty redemption, promotion wiring, a `Timer.periodic` and the sale submission path in one `State`. It is also the file every module has to touch, which is why Phase 2's four modules could not be split into separate PRs.

**M3 — Migration strategy is split two ways.** 15 versions live in `lib/core/database/migrations/`; the rest are inline `if (oldVersion < N)` blocks in `database_helper.dart` (679 lines). `MigrationV1` also has to delegate to V28 and V30–V33 to keep `onCreate` and `onUpgrade` in step — a coupling the PR #2 merge already had to unpick by hand once when v29 collided. Extracting the remaining inline versions and adding a test that creates a v1 database, upgrades it to 33, and diffs the schema against a fresh `onCreate` would make that class of bug impossible rather than merely caught.

**M4 — Secrets at rest.** `store_repository.dart:361` acknowledges storing the Razorpay key secret in plaintext SQLite; `google_drive_backup_service.dart:18` ships `'YOUR_GOOGLE_OAUTH_CLIENT_SECRET'` as a compiled-in constant. The Razorpay one is a real exposure on a shared shop PC — a restricted key plus OS-level DPAPI encryption of that column would be proportionate.

**M5 — 20 silent `catch (_)` sites**, including `sale_repository.dart:444`, `supabase_sync_service.dart:75` and two in `purchase_form_screen.dart` that are bare `catch (_) {}`. Failures in these paths are invisible. Only 5 `print` and 2 `debugPrint` calls exist app-wide, so there is no logging fallback either.

**M6 — GST compliance is a stub.** `gst_service.dart` is 11 lines: `amount * rate / 100` and its inverse. No CGST/SGST/IGST split, no HSN/SAC on the product model or invoice, no GSTR-1/3B export. For a Tamil Nadu retail business this is a statutory exposure rather than a feature gap, and it is the largest single piece of unbuilt work in the repository.

**M7 — Repository test coverage gaps.** 17 of 31 repositories have no test file, including `sale_repository`, `store_repository` (13.7 KB, holds every store setting and the gateway credentials) and `customer_ledger_repository`. 28 of 39 services likewise, including `invoice_service`, `day_end_report_service` and `promotion_engine`.

**M8 — `PR #3` is unmerged and the delay has a cost.** Until it lands, `main`'s copy of `tasks/phase2/PROGRESS.md` tells the next automated run that migration **33** is free, when `migration_v33.dart` exists. That recreates the exact v29 collision the PR #2 merge had to resolve by hand. It is a one-file docs PR with zero comments and zero reviews; merging it is the cheapest risk reduction available in this repository.

## 6. Low findings / housekeeping

- **`scr/` — 22 PowerShell generator scripts, ~1.06 MB**, largest 179 KB (`generate_complete.ps1`), untouched since 2026-07-30. These are the scaffolding that produced the original codebase (`fix_all_errors.ps1`, `fix_final_errors.ps1`, `fix_final_purchase.ps1`). They no longer reflect the code, cannot be re-run safely, and are 3× the size of `lib/`. Delete them — git history keeps them if ever needed. The folder name is also a typo for `src`, which invites confusion with real source.
- **`lib.zip` / `test.zip` at the repo root** are stale snapshots — `lib.zip` is missing 39 of the 244 current `lib` files. They are correctly `.gitignore`d now; delete the working copies too so nobody unzips one over live source.
- **Unused dependencies:** `excel: ^2.0.0` (zero imports — CSV export uses `csv`) and the bare `riverpod` entry (only `flutter_riverpod` and `riverpod_annotation` are imported).
- **Dead constants:** `AppConstants.sessionTimeoutSeconds` (session timeout is not implemented), `bonusPointsThreshold` and `bonusPointValue` (superseded by per-store settings in `store_repository.dart:139`). Leaving them implies behaviour that doesn't exist.
- **`README.md` still carries the stock "A new Flutter project… this project is a starting point" boilerplate** below three paragraphs of real content, on a 49 KLOC application.
- **9 generated `*.g.dart` files are committed.** Fine as a deliberate choice, but note `flutter pub get` rewriting `analysis_options.yaml` and `pubspec.lock` on every run is already a documented friction point that costs each automated run a `git checkout --`.
- **182 analyzer issues, 0 errors** (quoted). Stable, but 21 warnings have sat unaddressed across four verification runs; they are the cheapest quality win available.

## 7. Recommended order of work

**Week 1 — close the money holes.**

1. `cash_movements` table + single-writer cash accounting; `expectedCash` computed from it (C1).
2. Approval gate + `logAudit` + `session_id` on receive-payment (C2). Same change set as 1.
3. `reverseByReference` on sale cancellation (C3) — unblocks three Phase 2 modules.
4. Gate `/customers/form` on manager for credit-limit edits (H3).

**Week 2 — make the test suite mean something.**

5. Delete the 20 placebo test files in one commit (H1).
6. Real `sqflite_common_ffi` tests for `sale_repository`, following `gl_repository_test.dart`'s pattern.
7. Schema round-trip test: create v1 → upgrade to 33 → diff against fresh `onCreate` (M3).
8. Route-coverage test: every `GoRoute` path must appear in `_routeMinRole` (H3).

**Week 3 — stop the docs drifting again.**

9. Rewrite `FEATURE_STATUS.md` against the current tree (H2); merge PR #3 (M8).
10. Delete `scr/`, the zips, unused deps and dead constants (§6).
11. Clear the 21 analyzer warnings.

**Then, in priority order:** GST compliance (M6) — the largest real gap and the one with legal exposure; then Riverpod-ise data access feature by feature (H4) so widget tests become possible; then decide the three accounting questions Phase 2 escalated (loyalty liability, gateway fees, commission — all three want the same new chart-of-accounts entries, so treat them as one task); then split `billing_screen.dart`.

**Leave alone:** the GL design, the Phase 2 module architecture, and the `tasks/*/PROGRESS.md` convention. All three are working well and the journals in particular are why this audit could be specific rather than vague.
